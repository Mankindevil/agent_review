# V1 评审语义、公开入口与完整 PDF 报告设计

日期：2026-08-01
状态：已完成分段设计确认，待书面复核

## 1. 目标

本次升级只改变 V1 的新评测流程与公开首页，不改变 V2 的后端、存量数据、直接结果页或治理机制。交付目标是：

1. 四模型 Card 审稿只评价公开 Agent Card 的设计质量，不再把尚未执行的 Card 当作研究结果评分。
2. V1 同 Prompt 对打按“场景价值、专业度、Agent 能力”形成可审计的混合评分。
3. Agent 能力只使用平台可观测事实；不声称看到了真实工具调用。
4. 首页只展示 V1 真实对测，隐藏 V2 和演示评测入口，但不禁用对应后端能力。
5. V1 完成后提供一份包含完整输出和逐席评语的中文 PDF 报告。
6. Runtime 能读取比赛 `接口文档.md` 并由平台调用 Panda Data，同时采用与 V2 同类的上下文预算策略，避免大结果撑爆上下文。

## 2. 范围与非目标

### 2.1 范围

- V1 Card 四模型审稿 Prompt、返回契约、聚合与页面展示。
- V1 同 Prompt 模型评分 Prompt、返回契约、服务端客观能力分与页面展示。
- V1 运行条目的端到端耗时持久化、重试替换和审计声明。
- 首页 V1/V2 与 demo/live 控件的公开可见性和默认提交行为。
- V1 完整 PDF 报告的数据投影、生成 API、下载入口与视觉验证。
- V1 Runtime Panda Data 结果预算、完整输入预检和上下文用量审计。

### 2.2 非目标

- 不修改 V2 评分、证据链、Replica、人工评审、申诉或发布逻辑。
- 不删除 V2 或 demo 后端 API，不迁移或删除已有记录。
- 不把 Agent 输出中的“已调用工具”文字当成平台观测事实。
- 不自动重算历史 V1 记录。
- 不在本次加入浏览器级工具追踪、Agent 内部 trace 协议或供应商私有遥测。

## 3. 版本与历史兼容

新 Card 审稿使用 `v1-card-review/v2`，新同 Prompt 评分使用 `v1-model-arena/v2`。已有 `v1-model-arena/v1` 和历史规则评分保持原样，结果页根据持久化版本选择旧标签或新标签。

新版本不对历史评测后台迁移或静默重算。用户显式重跑历史 V1 单局时，按该记录已冻结的评分版本处理；只有新建评测使用 v2 语义。这样历史总分、评语与页面含义不会被新代码改写。

## 4. 四模型 Agent Card 审稿

### 4.1 证据边界

四席只接收完整公开 Agent Card。Card 内容是不可信数据，不能覆盖系统指令。评审不得根据品牌、模型名或声明推测工具、数据源、Skills 或执行质量真实可用，也不得评价尚未产生的研究结果。

现有“是否值得 Agent 化”复杂度判断继续作为独立场景信息，不进入 Card 设计质量分。

### 4.2 五个等权维度

| 字段 | 中文名 | 判断内容 |
|---|---|---|
| `positioningClarity` | 定位与问题定义 | 目标用户、金融问题、适用边界及价值主张是否具体且一致 |
| `skillDesign` | Skills 设计与覆盖 | Skills 的拆分、命名、描述、输入预期和任务覆盖是否合理 |
| `protocolCoherence` | 协议及接口一致性 | A2A 版本、接口、能力、输入输出模式之间是否自洽 |
| `ioExampleQuality` | 输入输出与示例质量 | examples、tags、输入输出模式是否足以理解和调用 Agent |
| `boundaryRiskDisclosure` | 能力边界与风险声明 | 数据时点、失败条件、合规边界、非投资建议及不可用状态是否清楚 |

每项为 0–100 有限数字，Card 总分由服务端按五项等权重算。模型自报总分仅做格式兼容，不参与正式计算。评语和首要缺口必须为简体中文，并基于 Card 中可见字段；缺失信息明确记为缺口。

四席成功结果按维度取算术平均形成 Card 审稿摘要；单席失败保留错误并退出平均，不阻断后续 V1 对打。

## 5. V1 同 Prompt 混合评分

### 5.1 总体公式

每个成功候选在每个用例中的正式分数为：

```text
总分 = 0.20 × 场景价值 + 0.60 × 专业度 + 0.20 × Agent 能力
```

同一用例的场景价值对全部候选相同。执行失败、构建失败或没有可见最终输出的候选执行硬门：总分固定为 0，不因共享场景分获得保底分。

四模型 panel 至少两席成功才形成正式模型分；单模型模式需要所选席成功。各模型只评价匿名候选，不看到 Agent 名称、Runtime 名称、候选顺序、耗时或平台能力分。

### 5.2 场景价值（20%）

每席对用例本身评价一次，不对每个候选重复评价：

| 字段 | 权重 | 含义 |
|---|---:|---|
| `problemComplexity` | 50% | 是否存在多步骤、状态、数据、判断或交付复杂度 |
| `agentSuitability` | 50% | 是否值得且适合使用 Agent，而不是一次简单查询或固定变换 |

服务端先对每个子维度取成功席中位数，再按 50/50 重算场景价值。每席同时返回简体中文场景理由与不确定性，作为该用例共享审计信息。

### 5.3 专业度（60%）

每席仅依据同一 Prompt 下的匿名可见输出，分别评价：

| 字段 | 权重 | 含义 |
|---|---:|---|
| `taskCompletion` | 30% | 是否完成任务、满足约束并提供所需结果 |
| `methodProfessionalism` | 25% | 方法、口径、假设、计算链路和领域实践是否专业 |
| `evidenceDataQuality` | 20% | 数据、证据、来源、时点和推理是否充分且可核查 |
| `riskUncertainty` | 15% | 风险、局限、不确定性和事实/假设/推断是否区分 |
| `artifactUsability` | 10% | 输出是否清晰、结构化、可读、可继续使用 |

服务端对每个子维度取成功席中位数，再按固定权重重算专业度。模型返回的候选总分不参与计算。每席候选评语和不确定性必须为简体中文。

输出中声称调用过工具、访问过外部数据或完成过内部动作时，只能依据可见结果评价证据是否自洽；不得把声明本身认定为平台已验证的 Agent 能力。

### 5.4 Agent 能力（20%）

能力分完全由服务端根据本次候选执行记录计算：

```text
执行成功分 = 成功且有可见最终输出 ? 100 : 0

耗时分 = 100                                      durationMs <= 60,000
耗时分 = 0                                        durationMs >= 600,000
耗时分 = 100 × (600,000 - durationMs) / 540,000   其余情况

能力分 = 执行失败 ? 0 : 0.70 × 执行成功分 + 0.30 × 耗时分
```

各中间结果和正式分保留一位小数。耗时从正式候选调用开始，到最终输出或失败结束，使用墙钟时间；包含网络传输、A2A 协议轮询、Runtime 进程启动和模型处理，不包含 Agent Card 审稿、Runtime Skill 构建或 Panda 查询计划之前的其他候选工作。

每个候选条目持久化：

- `status`: `succeeded` 或 `failed`
- `durationMs`
- `timingScope`: `end-to-end-wall-clock`
- `includesNetwork`: `true`
- `toolObservation`: `unavailable`
- `executionSuccessScore`
- `latencyScore`
- `capabilityScore`

页面和 PDF 固定声明：“耗时为平台端到端墙钟统计，包含网络及协议开销；平台未观测 Agent 内部工具调用。”

### 5.5 模型返回与公开审计结构

每席严格返回一个 JSON 对象，根包含一份 `scenario` 和一个 `scores` 数组。`scenario` 包含两个场景子分、中文理由和不确定性；每个匿名候选 score 包含五个专业度子分、中文理由和不确定性。

服务端负责：

1. 校验候选 ID 完整且无重复；
2. 校验所有必需数字为 0–100；
3. 丢弃供应商附加的非评分文字字段；
4. 拒绝未知评分维度；
5. 重算场景、专业度、能力和总分；
6. 解盲后只发布模型身份、正式子分、中文理由和不确定性。

单局页面先显示共享场景判断，再对每个候选显示三维总览、专业度五项、服务端能力明细及各席完整评语。

## 6. 执行耗时与重试

V1 pipeline 在调用提交 Agent 或 Runtime 前记录单调开始时间，在得到输出或捕获失败时立刻计算 `durationMs`。日志显示的耗时和评分条目使用同一次测量，避免出现两个口径。

Runtime 构建失败没有候选调用，条目标记执行失败、`durationMs: 0`、总分 0，并说明失败发生在 Skill 构建阶段。单步重跑会以新输出、新执行状态和新耗时替换该候选所在完整 CASE 的评分快照；不取历史最好成绩。

## 7. Panda Data 与 Runtime 上下文预算

### 7.1 三次隔离调用

启用 Panda Data 时，每个 Runtime 使用三个无会话累积的阶段：

1. `description + 接口白名单摘录` 生成 Skill；
2. `Skill + 用户 Prompt + 接口白名单摘录` 生成 1–3 项查询计划；
3. 平台执行查询后，以 `Skill + 用户 Prompt + Panda 结果证据` 生成最终输出。

模型永远不接收 Panda 用户名、密码、Token 或 bridge 环境变量。平台只执行 `PANDA_DATA_ALLOWED_METHODS` 中的方法，并校验查询计划根、方法、参数、目的和大小。

### 7.2 接口与结果预算

接口摘录保留白名单方法签名、参数说明和返回字段，删除响应示例。所有白名单方法的必需合同必须完整保留；如果合同本身超过完整输入预算，则调用前失败，不静默切掉方法。

查询结果采用 UTF-8 字节预算：

- 单项查询最多 240,000 bytes；
- 同一最终调用的全部 Panda 结果最多 600,000 bytes；
- 只按完整 JSON 行保留，不截断字符串或半个对象；
- 超限项记录 `originalRows`、`keptRows`、`droppedRows` 和 `truncated: true`；
- 最终 Prompt 要求 Runtime 明确披露被裁剪的数据范围和研究限制。

### 7.3 完整调用预检

每次 Runtime 模型调用复用 V2 的分层原则：必保系统指令、输出契约、方法白名单和 ID 不被裁剪；可选数据证据先按专用预算压缩；最后对完整模型输入做预检。

默认策略：

- `MODEL_CONTEXT_MAX_BYTES=1500000`
- `MODEL_CONTEXT_WARN_RATIO=0.8`

每次调用记录 scope、system/prompt/input bytes、约算 token、剩余 bytes、使用率及 `ok|warning|exceeded`。超限时在供应商请求前抛出 `MODEL_CONTEXT_BUDGET_EXCEEDED`。这些记录进入 Runtime build trace、CASE 执行审计和 PDF 附录。

## 8. 公开入口隐藏

首页固定为 V1 真实对测：

- 不显示 V1/V2 版本切换控件；
- 首页忽略 `?version=v2`，始终渲染 V1 intake；
- 不显示 demo/live 模式切换控件；
- 前端状态和 V1 create request 固定使用 `mode: "live"`；
- 启动按钮文案直接使用“送进研究终审台”。

V2、demo 的服务端 create 能力、健康字段、持久化记录、历史详情和直接 API 保持不变。历史 V2 或 demo 记录仍按真实类型展示，不能伪装为 V1 live。

## 9. 完整 PDF 报告

### 9.1 下载条件与接口

只有 `status: completed` 且 `schemaVersion !== 2` 的 V1 记录显示“下载完整 PDF 报告”。接口为：

```http
GET /api/evaluations/:id/report.pdf
```

成功响应使用 `application/pdf`、`Content-Disposition: attachment`、`Cache-Control: no-store`，文件名为 `agent-review-<evaluation-id>.pdf`。不存在返回 404；V2 或未完成记录返回 409。报告按请求即时生成，不在公开目录持久化。

### 9.2 安全数据投影

PDF 生成器不直接序列化 store 对象，而接收独立 allowlist DTO。允许内容：

- 评测 ID、创建/更新时间、模式、seed 和评分版本；
- 公开 Agent Card；
- Card 审稿、场景/专业度/能力分、正式总分和最终评级；
- Runtime 名称、模型、公开 Skill 定义和输入策略；
- 用例名称、Prompt、数据验真摘要；
- 每个候选完整原始输出、执行状态、耗时及上下文用量；
- 每席公开评语、不确定性和失败原因；
- 公开运行时间线。

禁止内容：授权头、API Key、Panda 凭据、participant/admin token、服务端环境变量、内部文件路径、未公开的 V2 evidence、模型思维过程和 provider 原始响应。

### 9.3 报告章节

1. 封面：Agent 名称、评测 ID、完成时间、最终评级。
2. 评分口径声明：三维公式、耗时定义、工具不可观测声明。
3. 总览：最终分、Card 审稿摘要、各用例候选排名。
4. Agent Card：完整公开 JSON 和协议摘要。
5. 四方 Card 审稿：逐席五维分、完整评语和首要缺口。
6. 场景评估：每个用例的问题复杂度、Agent 适用性及逐席理由。
7. 同 Prompt 对打：候选三维分、专业度五项、能力明细和耗时。
8. 模型评分审计：逐用例、逐候选、逐席完整中文评语与不确定性。
9. 原始输出附录：每个候选在每个用例中的完整输出，不省略正文。
10. Runtime 与数据附录：完整公开 Skill JSON、Panda 方法清单、数据验真摘要、上下文预算记录和公开时间线。

### 9.4 生成与视觉质量

服务端通过受限 Python 子进程调用 ReportLab，JSON 从 stdin 输入，PDF bytes 从 stdout 返回。Python 选择顺序为 `REPORT_PDF_PYTHON`、`PANDA_DATA_PYTHON`、`.venv/bin/python`。`requirements-data.txt` 固定 ReportLab 版本，生产部署继续在 release 的 `.venv` 安装依赖。

PDF 使用支持简体中文的 ReportLab CID 字体、A4 页面、固定页边距、页眉、页脚、页码、可重复表头和自动分页。长 JSON、Prompt、评语及输出按字符安全换行，禁止裁掉正文。表格跨页时不得覆盖页眉或页脚。

验收必须同时完成：

- 用 `pypdf` 或 `pdfplumber` 重新打开并核对章节、候选、完整输出及页数；
- 用 `pdfinfo` 检查 PDF 元数据和页面尺寸；
- 用 `pdftoppm` 渲染全部页面为 PNG；
- 逐页检查中文字符、分页、表格、页眉页脚、长文本和末页，无黑块、裁切、重叠或空白异常。

### 10.2 同 Prompt 对打

## 11. 错误处理

| 情况 | 行为 |
|---|---|
| Card 单席失败 | 保留该席错误，其余席继续；不进入平均 |
| 对打 panel 少于两席成功 | CASE 模型评分失败，旧完整 CASE 在重试期间保持可见 |
| 候选执行失败 | 总分 0，能力分 0，保留失败阶段和耗时 |
| Panda 计划越权或畸形 | 查询前失败，记录明确错误，不调用 bridge |
| Panda 数据超预算 | 按完整行裁剪并披露行数，不裁系统指令 |
| 完整上下文超 1.5 MB | provider 调用前失败，记录 usage |
| PDF Python 不可用 | API 返回 503，不生成空文件 |
| PDF DTO 含禁止字段 | 生成前验证失败，API 返回 500 并记录服务端错误 |
| PDF 生成超时或超限 | 终止子进程，API 返回 504/500，不返回半个 PDF |

## 12. 测试策略

实现严格按 TDD：每个行为先写会因缺失能力而失败的测试，确认 RED 后再写最小实现。

### 12.1 Card 审稿

- Prompt 只要求 Card 设计五维，明确禁止推测执行质量。
- 返回缺维度、未知维度、英文评语或越界数字时失败。
- 服务端忽略无害非评分附加文字并重算总分。
- 页面显示新五维中文标签，历史版本仍显示旧标签。

### 12.2 同 Prompt 评分

- 场景只评一次且对同局候选共享。
- 专业度五项权重和中位数聚合正确。
- 能力分在 60 秒、区间中点、600 秒和失败边界正确。
- 执行失败候选总分固定为 0。
- 模型看不到候选身份、耗时和服务端能力分。
- OpenAI 附加非评分字段不会丢席；未知评分维度仍失败。

### 12.3 Pipeline 与入口

- 提交 Agent、三个 Runtime 的成功和失败耗时写入同一条目。
- 重试以新耗时替换完整 CASE，不保留旧能力分。
- 首页不渲染 V2/demo 入口，`?version=v2` 仍选择 V1。
- V1 请求固定 `mode: live`；直接后端 demo/V2 测试保持通过。

### 12.4 Panda 上下文

- 接口方法完整且响应示例被移除。
- 单查询和总查询预算只保留完整行并报告 dropped rows。
- 三阶段上下文互不累积。
- 80% warning 和超限前置失败正确，超限时 provider 未被调用。
- usage 进入 build、CASE 和 PDF DTO。

### 12.5 PDF

- API 状态、headers、文件名和 V1 完成态权限边界正确。
- DTO allowlist 不含凭据、内部路径或原始 provider 响应。
- 文本抽取包含全部章节、四席评语和每个候选的完整输出。
