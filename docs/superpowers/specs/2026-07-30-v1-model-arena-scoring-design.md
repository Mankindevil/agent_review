# V1 大模型竞技评分设计

## 背景

V1 同题对测目前通过 `src/scoring.js` 的固定规则为每个输出打分：根据文本长度和金融关键词命中情况计算任务完成、数据证据、方法严谨和风险披露四维分，再加入稳定扰动。该规则无法理解输出语义，可能给“任务执行失败但包含足够金融关键词”的长文本较高分。

本次只修改 V1。V2 的绝对分、Replica Arena、人工评审和最终治理流程保持不变。历史 V1 记录不重算。

## 目标

1. 新建 V1 评测不再使用关键词规则或规则兜底。
2. 用户送检时可选择单模型同场评分或四模型匿名同场盲评。
3. 单模型模式允许选择 OpenAI、Anthropic、豆包或 DeepSeek；进入单模型模式时默认 DeepSeek，整个评分阵容控件仍默认四模型模式。
4. 所有分数可追溯到评分模式、模型席位、四维分和模型理由。
5. 候选执行失败与模型评分失败必须区分，不得用伪造分数掩盖基础设施故障。

## 非目标

- 不修改 V2 数据结构、评分权重、匿名 Arena 或评级阈值。
- 不重算已经存在的 V1 记录。
- 不为 V1 引入人工评审或 V2 的证据加密、bootstrap 和双轨治理。
- 不允许模型自报的总分覆盖服务端固定权重。

## 送检交互

V1 送检区新增“评分阵容”分段选择：

- `单模型`；
- `四模型匿名盲评`，默认选中。

选择“单模型”时显示模型下拉框，选项为 OpenAI、Anthropic、豆包和 DeepSeek，默认 DeepSeek。选择四模型时隐藏下拉框。

该控件放在 `legacy-only` 区域，只在 V1 表单显示。提交按钮仍使用现有 V1 入口。结果页每个 CASE 显示本次采用的评分阵容；历史规则评分记录显示“历史规则评分”，避免与新模型分混淆。

## 创建合同与持久化

V1 创建请求新增：

```json
{
  "scoringConfig": {
    "mode": "single",
    "reviewerId": "deepseek"
  }
}
```

或：

```json
{
  "scoringConfig": {
    "mode": "panel"
  }
}
```

约束如下：

- `mode` 只能是 `single` 或 `panel`。
- `single` 必须提供已登记的 `reviewerId`。
- `panel` 不接受 `reviewerId`。
- 新版网页默认提交 `{ "mode": "panel" }`。
- 为兼容旧 API 客户端，字段缺失时后端采用 `{ "mode": "single", "reviewerId": "deepseek" }`，但仍执行模型评分，不恢复关键词规则。

评测创建后将规范化配置和评分协议版本固化到记录：

```json
{
  "scoringConfig": {
    "version": "v1-model-arena/v1",
    "mode": "single",
    "reviewerId": "deepseek"
  }
}
```

`live` 模式在创建阶段校验所需模型是否配置：

- 单模型模式要求所选席位可真实调用。
- 四模型模式要求四个正式席位均已配置。

配置不足时创建请求失败并明确列出缺失席位，不启动 Agent 或 Runtime。`demo` 模式保留零配置体验，但模型分标为模拟评分，不冒充真实调用。

## 同场评分流程

每个 CASE 先完成提交 Agent 与全部 Runtime 的执行，再统一评分：

1. 执行失败的候选直接记 0，并记录 `scoreStatus: "execution-failed"`，不发送给模型。
2. 其余候选移除名称、Runtime ID 和顺序特征，为每个评委派生不透明候选 ID，并按固定 seed 打乱。
3. 评委同时看到共享任务与该 CASE 的全部匿名成功输出，不能浏览或调用工具。
4. 每位评委为每个候选返回四维分、理由和不确定性。
5. 服务端校验严格 JSON 合同，并根据固定权重重新计算总分：

```text
总分 = 0.40 × 任务完成与约束满足
     + 0.30 × 专业方法与结论质量
     + 0.20 × 证据与风险意识
     + 0.10 × 产物可用性
```

6. 单模型模式直接采用该席服务端重算后的总分。
7. 四模型模式对每个候选的四维分和总分分别取成功席位的中位数。

模型提交的 `total` 只做格式校验，不参与最终计算。评分温度固定为 0，seed 从评测 seed、CASE 和评委 ID 派生。

## 席位与失败处理

单模型模式使用用户选择的正式评审席，默认 DeepSeek。

四模型匿名盲评使用 OpenAI、Anthropic、豆包和 DeepSeek 四席。至少两席成功才形成 CASE 正式分数；一席或零席成功时：

- 成功执行的候选不生成数字分，显示 `—`；
- CASE 标记为“模型评分失败”；
- 保存各席失败原因；
- 不回退关键词规则、模拟分或历史分。

若一个 CASE 的所有候选都执行失败，则所有候选为 0，无需调用模型；这属于执行结果，不属于模型评分失败。

## 重试与派生结果

模型评分是同场比较。V1 任一候选使用“重跑这一局”后，系统必须重新匿名评审该 CASE 的所有成功输出，并整体替换该 CASE 的旧评分快照，不能只给重跑候选单独评分。

只有所有 CASE 都具有正式数字分时，才计算：

- 每个候选跨 CASE 平均分；
- 与 Claude、豆包基线的差值；
- 最终“夯 / 人上人 / NPC / 拉”评级。

如果存在模型评分失败的 CASE，保留已经完成的输出和评分审计信息，但不生成最终评级。

## 模块边界

新增独立的 V1 模型竞技评分模块，职责为：

- 规范化 V1 评分配置；
- 构建匿名同场评分包；
- 调用单席或四席模型；
- 校验返回值并按固定权重聚合；
- 返回不含真实候选身份映射的公开评分结果。

该模块复用 V2 的匿名评分提示词、四维键名和固定权重语义，但不依赖 V2 的 EvidenceVault、Replica 数据结构或治理状态机。V1 pipeline 只负责收集一个 CASE 的执行结果、调用评分模块并持久化结果。

关键词 `judgeOutput` 不再参与新 V1 流程。若为兼容测试暂时保留该导出，应明确标记为 legacy，不能被 pipeline 调用，也不能成为模型失败的 fallback。

## 数据展示

每个候选条目继续显示最终分数，并新增可审计信息：

- 评分状态；
- 单模型名称，或“四模型匿名盲评 · 成功席位数/4”；
- 聚合后的四维分；
- 各成功席位的理由与不确定性；
- 失败席位及失败原因。

界面输出必须经过现有 HTML 转义。匿名候选 ID 与真实身份的映射只在服务端评分调用期间存在，不写入公开结果。

## 测试与验收

### 单元测试

- 评分配置仅接受 `single` / `panel` 及合法 reviewer ID。
- 缺失 V1 配置时规范化为 DeepSeek 单模型。
- 服务端按 `40/30/20/10` 重算总分，忽略模型自报总分。
- 四席聚合使用中位数。
- 单模型失败、四模型不足两席成功时不产生数字分。
- 执行失败固定为 0，且不会出现在模型评分包。
- 候选匿名 ID、顺序和模型返回值不能泄露真实 Runtime 身份。

### Pipeline 测试

- 新 V1 评测不会调用 `judgeOutput`。
- 单模型模式只调用所选席位。
- 四模型模式调用四席并持久化聚合结果。
- 任一候选重跑会重新评分整个 CASE。
- CASE 评分失败时不生成 averages、roast 或最终评级。
- 历史 V1 记录仍可读取并标记为历史规则评分。
- V2 测试保持不变。

### UI 测试

- 评分阵容控件只在 V1 显示。
- 四模型为默认选择。
- 单模型模式显示模型下拉框，默认 DeepSeek。
- 请求体准确携带 `scoringConfig`。
- 结果页正确显示评分阵容、失败状态和非数字占位符。

## 验收标准

1. 新 V1 评测不存在关键词规则评分路径或规则 fallback。
2. 用户能在送检时选择单模型或四模型匿名盲评；四模型为整体默认，切换到单模型时 DeepSeek 为模型默认值。
3. 截图中“失败说明写得很长却获得 75 分”的情况不再发生：执行失败恒为 0；成功但未完成任务的输出由模型按语义判断。
4. 四模型模式不足两席时明确失败，不伪造最终数字。
5. V2 行为与结果保持完全不变。
