每一分，
到底怎么来的？

这不是一句“模型觉得不错”。下面公开当前代码实际执行的校验条件、公式、失败处理和最终分档顺序。看完后，你应该能够用同一份输入手工复算大部分结果。

先说结论 评分是可比较的工程信号，不是真理。

当前必要性与输出质量使用透明启发式；专业度由多模型给分。它适合产品验收和相对比较，不应替代法律、医疗或安全审计。

STAGE 00 / GATE

A2A 协议准入

这一阶段只决定“能不能进入考场”，不产生分数。

必须满足

  • Agent Card 是 JSON 对象；
  • 存在非空 name 与 description；
  • 至少声明一个 skill；
  • 每个 skill 都有 id / name / description；
  • 存在 A2A 1.0 supportedInterfaces，或兼容 0.3 的顶层 url。

失败如何处理

HTTP 400

任一必填项缺失，创建评测直接失败，不会用 0 分假装跑完。Card URL / 服务发现还会检查 HTTP(S)、私网地址限制、1 MB 响应上限与禁止重定向。

支持 HTTP+JSON、A2A 1.0 JSON-RPC SendMessage 和 0.3 message/send。
STAGE 01 / RULE ENGINE

Agent 必要性：五维等权

判断固定 Agent 流程是否真的比一次模型调用更有价值。满分 100，五个维度各占 20%。

C命中的复杂信号组数量，最多 8 组
S是否出现简单变换信号，当前为 0 或 1
KCard 中声明的 skill 数量
N测试用例数量，范围 1–5
U是否提供测试用例；正常提交恒为 1
B能力加分：流式 +5、推送 +6、扩展 +4

复杂信号组：多步编排、人机确认、外部系统、文件文档、跨文档核对、证据/合规、状态/异步、规划/重试。每组无论命中几次只计一次。
简单信号：整理文件、重命名、摘要、翻译、改写、分类、format 等。

步骤深度clamp(18 + 10C − 5S)复杂步骤加分；简单变换扣分。
工具依赖clamp(12 + 9C + 3K)复杂信号与 skill 数共同反映工具编排需求。
状态与分支clamp(10 + 8C + B)Card 声明的 streaming、push 与 extensions 进入能力加分。
不确定性clamp(22 + 8U + 5C)需要澄清、判断和恢复的任务更适合 Agent。
复用价值clamp(26 + 7K + 4N + 4C)skill 与测试场景越多，固定流程复用价值越高。
必要性总分round((五维分数之和) ÷ 5)所有维度先限制到 0–100。
0–35模型直出更划算最终评级强制为“拉”
36–59Agent 价值存疑允许继续实战对比
60–100值得 Agent 化多步、外部依赖或状态信号充分
STAGE 02 / MODEL PANEL

专业度：多模型独立盲审

评审只看公开 Agent Card；必要性分只作为背景，不能直接复制为专业度分。

维度主要看什么常见失分项
领域深度约束、术语、证据与业务边界只有泛化描述，没有领域规则
流程设计步骤顺序、分支、工具与人工节点“分析并输出”式空流程
异常处理超时、缺参、失败恢复、回滚与升级默认永远成功
输出契约格式、字段、证据和完成定义只有自然语言承诺，无可解析结构
可评测性示例、验收点、成功/失败判据无法从可见结果判断是否完成

单模型返回

{
  "score": 0-100,
  "dimensions": { "五个维度": 0-100 },
  "comment": "简评",
  "risk": "首要风险"
}

当前后端使用模型返回的 score 作为该评审总分，不会再从五个维度二次求平均。

汇总公式

有效评审分之和 ÷ 有效评审数
  • 成功且 score > 0 才进入平均；
  • 调用失败保留错误并显示 0，但不进入平均；
  • 全部失败时专业度为 0；
  • 专业度目前用于报告与审计，不直接决定最终四档评级。
DEMO 模式使用输入 Card、评审 ID 和 seed 生成确定性模拟分；它用于走通产品流程，不代表真实模型意见。
STAGE 03 / RECONSTRUCTION

Runtime 现场复刻：先造 Skill，不在此处打分

Claude Code、Cursor Agent、Doubao Agent 只拿到同一份 Agent Card，不拿原 Agent 源码、隐藏提示词或历史输出。

1读取 Card相同公开描述
2生成 Skillname / description / instructions / tools
3结构校验无效 JSON 自动纠错重试一次
4进入对打用原始用户 prompt 执行

构建成功

记录 Runtime、模型、执行模式、Skill 指纹、seed 和可见结构。构建阶段本身没有 0–100 分，避免拿“会写 Skill JSON”冒充任务能力。

构建失败

该 Runtime 仍保留在对战表中，但每个测试用例都会生成失败条目，实战分强制为 0。其他 Runtime 与提交 Agent 继续执行。

STAGE 04 / ARENA

同 Prompt 对打：只看可见最终输出

每个用例分别运行提交 Agent 与三个复刻 Skill。评分器不读取隐藏思维链，也不因为模型品牌加分。

任务完成76

输出长度大于 25 字符；否则 42。

依据证据83

出现“因为 / 依据 / evidence / source / 文件 / 步骤 / 结果”等信号；否则 60。

结构表达82

存在换行、项目符号或编号列表；否则 62。

可用性45–75

45 + min(输出长度, 900) ÷ 30

单局实战分round(clamp(四维均值 + seed 稳定扰动))稳定扰动范围 −5 到 +5；执行失败时无论公式结果多少都覆盖为 0。

多用例汇总

每个选手的实战均分 = 该选手所有测试用例分数的算术平均，保留 1 位小数。

“同 Prompt”的含义

提交 Agent 收到原始 prompt；Runtime 执行提示会带上刚生成的 Skill，但其中的用户原始 prompt 不改写。当前评分不使用用例中额外的结构化验收点。

当前启发式的已知偏差较长、有列表、出现“依据”等词的输出更容易得分；它无法验证事实真假或领域结论正确性。生产版应增加规则断言、独立 Judge 与人工抽检。
STAGE 05 / FINAL VERDICT

最终分档：按顺序命中第一条

设 A 为提交 Agent 实战均分，C 为 Claude Code 均分，D 为豆包均分，N 为必要性分。

1拉N < 36

任务不值得 Agent 化。即使实战分高，也先判“拉”。

2夯A − C ≥ 3

提交 Agent 明显压过 Claude Code 复刻基线。

3人上人0 ≤ A − C < 3

不低于 Claude Code，但领先不足 3 分。

4拉A − D < 0

低于 Claude，同时连豆包基线也没守住。

5NPC其他情况

低于 Claude，但不低于豆包。

顺序很重要：必要性不足拥有最高优先级；“低于豆包”的判断发生在“不低于 Claude”的判断之后。专业度均分当前不会改变这棵分档决策树。

STAGE 06 / REVIEW CONTROL

单步重试与综合重算

重试不是多跑几次挑最高分，而是用最新结果替换旧结果。

重跑模型

只替换指定 reviewer 的专业度结果，再计算有效评审平均。

重建 Runtime

替换 Skill，并重新执行所有同 Prompt 对测用例，避免构建物与输出版本错位。

重跑一局

只替换某个用例中的某位选手结果。

重试完成后专业度 → 各选手均分 → 差值 → 最终分档，全部重算前后摘要、耗时与目标 key 写入 retryHistory；最多保留最近 100 条。
固定 Seed

根 seed 会为每个 reviewer、Runtime、用例和 Judge 派生稳定子 seed；单步重试沿用相同子 seed。OpenAI-compatible 与方舟链路会发送 seed，Cursor CLI 和外部 A2A Agent 只能尽力复现。

STAGE 07 / DISCLOSURE

你应该如何解读结果

报告同时标注 LIVE、DEMO、RULES、FAILED 或 MIXED，避免把模拟产物误认为真实调用。

能说明

同一套公开规则下的相对表现、Agent Card 的工程完整度、可见输出质量、各适配器是否成功。

不能说明

事实绝对正确、业务长期稳定、生产安全、成本最优，或某个模型品牌的普遍能力。

下一版重点

结构化验收断言、匿名随机排序、独立 Judge、重复采样置信区间、成本与耗时进入报告。
